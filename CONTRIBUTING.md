# Contributing

## Build and test

Use Node.js 22.12 or later. `@vscode/vsce` 4 needs that minimum to package.

```bash
npm ci
npm run compile      # or: npm run watch
npm test             # listens on temporary 127.0.0.1 ports
npm run style:check  # Biome format and lint; npm run format rewrites
npm run package:vsix
```

The tests run against simulated VS Code APIs with real loopback callbacks and locks. They do not start VS Code, so they cannot show how the editor selects, forwards, or restarts an MCP server. Check those in a real window, including a Remote SSH window and a Copilot session, before a release.

Press `F5` to launch the Extension Development Host. With no saved sign-in, the connection prompt must appear before any browser opens, and no RDH server may be listed until sign-in completes.

## How sign-in behaves

These rules are deliberate. Change them only on purpose.

- The MCP server is published only while a sign-in is saved, and the definition carries the credentials. A definition without them would send VS Code into its own OAuth flow.
- The first time VS Code looks for the server, the extension asks once whether to connect. After a declined, cancelled, or failed attempt, or after **Sign Out**, only **Sign In** starts authentication.
- A window with a saved sign-in keeps it renewed in the background. A window that has never signed in contacts nothing.
- Windows on one host share the sign-in and take turns through a loopback lock, so a refresh token is rotated once.
- VS Code deduplicates MCP servers by name. The extension and the agent plugin both use `remote-device-hub`, but their sign-ins are separate.

## Layout

| Path | Purpose |
| --- | --- |
| `src/extension.ts` | Activation, commands, and the MCP server definition provider |
| `src/authSession.ts` | Sign-in, token refresh and recovery, sign-out |
| `src/authDiscovery.ts`, `src/authCallback.ts` | OAuth metadata discovery and the browser callback server |
| `src/credentialStore.ts`, `src/credentialLock.ts` | Secret storage format and the cross-window lock |
| `src/boundaries.ts` | Validation of saved credentials and OAuth responses |
| `src/deploymentDefaults.ts` | Generated by `remote-device-server/tools/ops/sync-deployment.py`; do not edit |
| `skills/remote-device-operations/` | The operating skill, shipped in the VSIX and in the plugin package |
| `plugin.json`, `mcp.json` | Agent Plugins package for clients that do not load the extension |
| `scripts/sync-skill.cjs` | Copies the skill to the other plugin checkouts |

## The operating skill

This repository is the single source of `skills/remote-device-operations/`. With the other plugin checkouts next to this one:

```bash
npm run skill:check  # report drift without writing
npm run skill:sync   # copy the skill into them
```

Pass `-- --target <checkout>` to select checkouts and `-- --workspace <dir>` when they live elsewhere. The only permitted differences are the host-specific replacements listed in `scripts/sync-skill.cjs`, and each must match the source exactly once. `remote-device-plugin-claude` is synced. The Codex and DSH plugins carry their own skill text.

CI has only this checkout. It verifies that the replacements still apply, and cannot compare the other repositories, so run the check before a release.

## The agent plugin package

`npm test` validates `plugin.json`, `mcp.json`, and every `SKILL.md`, and requires the plugin version to equal the extension version. To try the package in VS Code, register this checkout with the experimental `chat.pluginLocations` setting, start a Copilot session, and run `/remote-device-hub:remote-device-operations`.

## Server integration tests

Optional. They drive the compiled extension against a disposable local Hub and need the `remote-device-server` checkout with its development dependencies and `RDH_TEST_POSTGRES_DSN` pointing to a disposable PostgreSQL database.

```sh
RDH_SERVER_ROOT=/path/to/remote-device-server
PYTHONDONTWRITEBYTECODE=1 "$RDH_SERVER_ROOT/.venv/bin/python" -m pytest \
  -q -p no:cacheprovider -c "$RDH_SERVER_ROOT/pyproject.toml" \
  -o "pythonpath=$RDH_SERVER_ROOT/tests/support $RDH_SERVER_ROOT $RDH_SERVER_ROOT/tests" \
  test/server/test_signout.py
```

`test/server/test_split_auth.py` runs the same way and also needs `RDH_TEST_RUST_AUTH` and `RDH_TEST_RUST_MIGRATE` set to matching Server binaries.

## Releasing

Bump the version in `package.json`, `package-lock.json`, and `plugin.json`, move the `CHANGELOG.md` entries under the new version, and push to `main`.

`.github/workflows/release.yml` does the rest. When `package.json` names a version that has no GitHub Release, it checks style, runs the tests, packages the VSIX, creates the release `v<version>`, and publishes that same file to the VS Code Marketplace. A push that does not change the version does nothing.

Publishing uses Marketplace Trusted Publishing, so the repository stores no publishing secret. It needs a policy on the `easelian` publisher, under **Trusted Publishing** in the [publisher management page](https://marketplace.visualstudio.com/manage/publishers/), with repository owner `easelian`, repository `remote-device-plugin-vscode`, workflow `release.yml`, and no environment. Without it, the release is still created and only the publishing step fails.

To publish a version whose release already exists, run the workflow by hand from `main` under **Actions > Release VSIX > Run workflow**. It downloads the VSIX from the release and publishes it. A version already on the Marketplace is skipped.
